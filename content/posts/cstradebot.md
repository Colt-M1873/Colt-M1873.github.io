CS2 里的枪械皮肤可以在网易 BUFF 上自由买卖，这是一个有真实流动性、真实价格波动的市场。跟股票、期货一样，这里也有买卖价差：同一件商品，"求购价"（别人愿意花多少钱收）和"在售价"（别人愿意多少钱卖）之间总有个缺口，价格本身也会随时间涨跌。

我做的这个项目，出发点很朴素：能不能用数据判断"现在按求购价买入这件商品，过一段时间大概率能以更高价卖出"，然后让程序自动去挂求购单，不用人盯着。做到现在，这已经变成一个从数据采集、数据库设计、机器学习建模，到自动化下单执行的完整系统，而且是跑在真实账户和真实资金上的，不是纸面回测。

下面我按整体架构、数据模型、交易策略、建模方法、回测这几块分别讲讲，尽量说清楚每一部分具体是怎么设计的、为什么这么设计。

## 零、好奇的起点：最简单的秒杀系统至今有效

这个项目最开始跟"系统""架构"这些词一点关系都没有。

我平时就有刷 BUFF 看看饰品价格的习惯，纯粹是玩家心态。刷得多了会发现一个现象：偶尔会有卖家可能是急用钱、可能是手滑、也可能就是懒得比价，直接把一件东西挂出一个明显低于市场行情的价格。这种单子如果被人先看到先买，基本就是白捡的便宜。问题是这种单子出现的时间不固定，也不会一直摆在那儿等你，稍微晚个几分钟大概率就被别人捡走了。人肉盯盘显然不现实，我不可能一天24小时开着页面刷新。

正好那段时间 BUFF 上线了官方开发者 API，能查到实时的挂单价格和数量。我当时没想那么多，就是觉得"这玩意儿能自动查价格，那不就能自动帮我盯盘了"，抱着玩一玩的心态买了 API 额度试试。最开始做的事情特别简单：写个脚本定时把关心的商品价格拉下来存进数据库，再跟数据库里存的上一次价格做个对比，如果发现哪个商品价格突然跳水跳得比较狠，就给自己发一封邮件提醒。邮件一响，人再手动打开 BUFF 去确认、去手动下单抢购。

这套东西断断续续跑了大概一个月，还真的靠着这些"捡漏"提醒赚到了一点钱——不多，但足够让我确认这个思路是成立的：**价格的异常波动是可以被数据发现、被自动化盯住的，剩下的只是"发现了之后怎么处置"这个问题要不要也交给程序去做**。后面所有的数据库设计、行情聚合、机器学习建模、自动化下单，其实都是在这套最原始逻辑上一步步往外长出来的。

这个跌幅监控本身逻辑不复杂，我保留到现在还在跑，简单讲一下原理：

它没有单独起一个定时任务，是挂在负责抓取全量商品价格的脚本上的——那个脚本本来就是每5分钟拉一次全市场的最新价格、写进数据库，写完之后顺手做一次监控，不用再单独发一次请求。监控的核心就是拿"数据库里存的上一次价格"和"这次API刚抓回来的当前价"做对比，算一个跌幅百分比。

阈值不是写死一个数，而是按价格分档：普通商品默认跌超过7%才报警，价格超过500的商品门槛收紧到5%，超过1000的收紧到4%——贵的东西哪怕跌的百分比不大，绝对金额上能捡的便宜也更可观，所以门槛适当放低一点。光看这一个跌幅条件其实还不太够，因为价格短期抖动很正常，光跌了不代表真的便宜，还得看它相对最近一段时间是不是真的偏离了——所以后来我又加了一层过滤：要求当前价相对7天和30天的滚动均价都明显偏低，而不只是相对上一条记录偏低，这样才能把"正常波动"和"真的捡到便宜"分开一些。符合条件的商品会按跌幅排个序，取跌得最狠的前十个，拼成一封邮件，标题里直接带上商品名、现价、跌了多少个点，正文里再附上直达链接，一封邮件发出去，人在手机上一眼就能看到该不该马上去抢。

现在回头看，那会儿搭的其实是这个项目最早、也是最简单的一版系统，链路就四步：**API 拉价格 → 存数据库 → 跑价格监控代码 → 发邮件提醒 → 我自己手动去下单**。没有模型、没有策略池、没有自动下单，人是链路里最后一环，也是唯一做决策的一环。但正是这个"能跑起来、还真能赚到钱"的最小闭环，给了我继续往下做的信心——后面要解决的问题无非是把人工的那几环一点点往自动化上搬：怎么不只盯着"价格跌了"这种表层信号，而是预测未来会不会涨；怎么让程序自己判断该不该买、该出多少钱；怎么让这套东西7x24小时稳定跑而不用我盯着。这些问题的答案，就是接下来几章要讲的整体架构。

## 一、整体架构：五层流水线

整个系统是单机部署的，没有上微服务那一套，用 Linux 的 systemd 管理十几个定时任务和常驻服务，数据库单独用 Docker 跑了个 MySQL 容器。架构上大致可以拆成五层，数据从最底层往上一路"提纯"，最后变成具体的下单动作：

```
┌──────────────────────────────────────────────────────┐
│ ① 数据采集层                                             │
│   7x24小时爬虫 + 5分钟级快照，抓全量与高流动性商品的      │
│   在售价/求购价/数量                                      │
└───────────────────────────┬──────────────────────────┘
                             ▼
┌──────────────────────────────────────────────────────┐
│ ② 数据聚合与流动性筛选层                                  │
│   小时/日/滚动均价聚合；用价格变化频率代理成交频率，        │
│   筛出真正有流动性的标的                                   │
└───────────────────────────┬──────────────────────────┘
                             ▼
┌──────────────────────────────────────────────────────┐
│ ③ 建模与信号生成层                                       │
│   XGBoost 每日更新特征、推理，预测8天后能不能覆盖手续费，   │
│   产出精选/非精选两套目标池                                │
└───────────────────────────┬──────────────────────────┘
                             ▼
┌──────────────────────────────────────────────────────┐
│ ④ 采购决策与执行层                                       │
│   多池策略配置 → 安全过滤 → 利润率排序 → 算出该撤该买的     │
│   订单 → 调用官方API下单                                  │
└───────────────────────────┬──────────────────────────┘
                             ▼
┌──────────────────────────────────────────────────────┐
│ ⑤ 运维与监控层                                          │
│   systemd定时调度、数据新鲜度巡检告警、数据库云端备份       │
└──────────────────────────────────────────────────────┘
```

每一层之间是靠数据库表和 CSV 文件解耦的，不是代码直接调用。好处是任何一层想单独改动或者重启，都不会牵一发动全身——比如模型换了个版本，只要产出的 CSV 路径不变，下单脚本完全不用动；爬虫这边要是哪天限流了，也不会直接把下游的建模、下单流程搞崩，顶多是数据新鲜度告警响一下。

这种分层加上后面会讲的"配置驱动"思路，是我在这个项目里比较刻意坚持的一条设计原则：**尽量让策略调整这件事，不需要碰代码**。

## 二、数据模型：从原始快照到特征表

数据库是 MySQL，用 SQLAlchemy 写的 ORM，表结构基本都定义在一个 `goods_orm.py` 文件里。设计上有几个我自己觉得还算讲究的地方：

**主键设计**。所有带时间维度的表，主键都是"时间字段 + 商品ID"的复合主键，这样既能让同一个商品在不同时间点反复写入，又能天然支持"重复写入就更新"（`ON DUPLICATE KEY UPDATE`）的幂等写法，不用在业务代码里自己判断"这条记录是不是已经存在"。只有字典类的表（比如商品基本信息、N日均价汇总）才用商品ID做单列主键，代表"每个商品只留最新这一条"。

各层级的表大致是这样串起来的：

```
goods_sales_price（5分钟级全量快照，最原始的表）
   │ 按小时聚合
   ▼
goods_hourly_avg_price ──按日再聚──▶ goods_daily_avg_price
                                            │ 汇总近1/3/7/15/30天
                                            ▼
                                  goods_rolling_avg_price（滚动均价，供风控用）

goods_trade_info_realtime / goods_trade_info_realtime_high_liquidity
（常驻爬虫抓的精细行情：在售价、求购价、挂单量……）
   │ 按天聚合
   ▼
goods_trade_info_daily
   │
   ▼
xgboost_features_v5 / xgboost_features_v6（特征表，喂给模型训练和推理）
   │ 推理产出信号CSV
   ▼
求购目标池（精选池 / 非精选池）
```

还有一张单独统计"价格变化次数"的表，专门用来判断一个商品到底活不活跃——这个我在下一节数据洞察里细讲。

比较有意思的一个设计取舍是"快照表"：像 `goods_sales_price` 这种表体量很大（几千万行往上），如果监控脚本每次都要在这张表上做"找出每个商品最新一条记录"这种全表聚合查询，性能会很差。所以我额外维护了一张 `goods_latest_price`，每个商品只存一行最新状态，主表每次批量写入的同时顺带把这张表也更新一下，专门给需要"查最新价"的场景用，不用去扫大表。类似的思路在"价格变化统计"那张快7GB的大表上也用了——单独建了一张按商品预先汇总好的表，加上覆盖索引，把"哪些商品交易最活跃"这类查询从扫全表变成走索引。

模型相关的表有个演进痕迹：早期版本、V5、V6 三套特征表是分开建的，字段逐代增加而不是直接改老表结构。这是有意为之——新模型上线不会影响正在跑的旧模型，出问题也方便直接切回旧版本，代价是数据库里同类的表会多存几份，但我觉得这个代价换稳定性是值得的。

## 三、交易策略：配置文件驱动的多池求购

模型算出信号之后，真正要花钱下单的这一步，我把逻辑设计成了"多策略池"的形式，核心思路是**不同来源的候选商品，应该用不同的信任程度对待**。

具体来说，线上现在跑着两个池子：一个是"模型精选池"，装的是 XGBoost 判断大概率能在8天后覆盖手续费还有得赚的商品，这个池子的利润率门槛设得很低（4%），因为我选择相信模型的判断，宁可多接一点；另一个是"高流动性但模型没选中"的池子，作为补充，但门槛设得非常高（80%），只有价差大到很夸张的情况才会碰这个池子里的东西，算是"漏网之鱼"里挑最保险的。

这两个池子、各自的利润率门槛、要不要额外做风控过滤、重叠了怎么处理，全部写在一份 JSON 配置文件里，改策略就是改这份配置，不用碰下单脚本的代码。换模型版本（比如从V5切到V6）也是一样，改一下配置里 CSV 文件的路径就行。这个设计当时是为了应对一件具体的事：模型迭代很频繁，如果每次调参、换版本都要改代码重新发布，出错的概率和运维负担都会上升，配置和代码分离之后，改动范围可控多了。

在真正下单前还有一道风控——安全过滤。逻辑是拿商品最近3/7/15/30天的滚动均价，跟当前最新的在售价做比较：

- 如果现价相对7日均价涨太多，可能是短期炒作，不追；
- 如果现价相对30日均价跌太多，或者3/7/15/30天的均价呈现出连续下跌超过3%这样的下行趋势，可能是正在跌的坑，不接；
- 只有落在一个相对温和的区间（现在生产上用的是跌不超过15%、涨不超过5%这个范围）才会进入候选。

定价策略我反而做得很简单：直接追平当前市场最高求购价，不额外加价抢排队顺位。代码里其实留了一套按价格档位分级加价的逻辑（低价商品加一毛、中价加一块、高价加十块），是早期验证阶段用过的方案，现在关掉了。倒不是加价没用，而是我更倾向于把复杂度花在"选对标的"上，价格上多争一点排队顺位，对整体收益的边际贡献远不如选股准不准。

另外提一句下单前的强制检查：脚本每次真正执行下单动作之前，都会先查一下店铺的求购状态是不是在线，不在线就直接跳过这一轮，不会硬着头皮发请求。所有改动上线前也都习惯先跑一遍 `--dry-run`，把整个筛选、排序、决策过程完整走一遍但不实际发请求，日志里能看到"这一轮本来准备撤哪些单、买哪些单"，确认没问题了才会去掉这个参数。

BUFF 平台对单个商品每天的求购操作次数是有上限的，我们最早是每10分钟跑一轮策略，跑一段时间后发现某些换手快的商品容易顶到这个上限——因为"先撤旧单再按最新价重新下单"这个动作本身就会消耗一次操作配额。后来把轮询频率降到了每30分钟一次，同时给人工手动设置的长期求购单加了一份白名单，让自动化策略不要去反复撤销重挂这些单子，两个改动加起来把触发平台限制的概率降低到了可以接受的水平。

## 四、建模方法论：预测8天后能不能赚钱

模型这块，预测目标我定义得比较明确：**判断一件商品在8天之后，价格能不能覆盖2.5%的卖出手续费**。不是简单判断"现在便宜不便宜"，而是往前看8天，算一笔扣完手续费之后到底划不划算的账，用对数收益率去建模。

特征主要在对数价格空间里构造：不同周期的价格滞后和差分、均线和波动率、动量信号、在售数量的变化趋势、商品本身的属性（磨损、稀有度、品质），再加上全市场层面的整体趋势特征——这部分特别要注意时间对齐，训练的时候必须把目标值往后移，不然很容易不小心把未来的信息漏进特征里。

模型迭代了一版，起初只用了在售（卖盘）那一侧的信息，后来我猜测买卖双方的力量对比应该也有解释力，就加了一批求购（买盘）侧的特征——求购价、求购量的变化趋势，还有价差、盘口深度比这类刻画买卖双方博弈强度的指标。新旧两个版本我是完全独立并行跑的，各自有自己的数据表、推理脚本、定时任务，图的是不管新版本表现怎么样都不影响线上已经稳定跑着的旧版本，随时能切回去。

验证效果的时候，我拿两个版本在同一段97天的历史区间里做了同口径对比：按每天选出的Top10/20/50/100商品，分别统计扣完手续费之后的日均净收益率和胜率。新版本是全面胜出的——Top10这一档，日均净收益率从11.14%涨到13.84%，胜率从73.2%涨到79.4%，其他几档也都有类似幅度的提升。

除了这种直接对比，我还专门做过一次统计显著性检验，想确认模型选出来的商品跟随机选的到底有没有本质区别——用蒙特卡洛方法从同一个商品池里随机抽了5000次做对照，把模型结果放到这个随机分布里看落在什么位置。这次检验其实给了我一个反直觉的结果：模型选出来的Top100商品，在"价差大小"这个指标上反而低于随机抽样的平均水平。后来想明白了，价差小往往说明这个商品交易更热门、买卖盘竞争更充分，模型学到的其实是"偏向选热门标的"这么一个倾向，跟"收益好不好"不是一回事，得靠前面那种基于真实8天收益率的回测才能回答收益的问题。这次检验没白做，至少让我确认了一件事：不能光看一个统计指标就下结论，得结合业务含义具体分析。

## 五、回测：用科学一点的方法验证策略

除了机器学习这条线，我还专门搭了一套回测框架，验证一个更朴素的价格动量反转信号是否有效——逻辑是当一件商品的当前价格相对30天均价明显偏低时，可能存在反弹机会，回测就是要验证这个直觉站不站得住脚。

回测这块我比较在意方法论上不要踩坑，具体做了这么几件事：

每一次策略回测，都同步跑一组"同等数量随机买卖"的基线，而且不是跑一次，是重复上百次取统计上的均值和区间，这样才能判断策略赚钱到底是真有效还是纯属运气好。信号计算严格只用当天以及之前的数据，不会不小心用到未来的价格。候选商品池是按"当时真实能交易的那批商品"来确定的，不会拿"后来还活跃到现在"的商品去美化回测结果，不然很容易产生幸存者偏差。关键参数（比如信号阈值、持有天数、样本量）都做了网格扫描，看策略是不是在一个小范围内都还稳健，而不是恰好卡在某一个点上好看。

这套方法跑下来，也确实发现了一些有意思的市场规律：这个市场大体上呈现"多数时间比较平淡、少数交易贡献了大部分收益"这种不对称的特征；价格短期偏负、中期中性偏低的商品更容易出现反弹；把2.5%的真实卖出手续费算进去之后，很多原本看着不错的信号会明显变弱——这提醒我交易成本在这种偏高频的操作里必须认真对待，不能只盯着毛收益看。

## 六、工程与稳定性

系统能不能"跑起来"和能不能"7x24小时稳定跑"是两码事，这块我做的主要是这几件事：

用 systemd 把十几个定时任务和几个常驻爬虫服务化管理，每个任务各管各的，一个出问题不会连累别的。专门做了一套数据新鲜度巡检，每小时去查几张核心表的最新更新时间，一旦哪个环节卡住了（爬虫掉线了、聚合任务跑失败了），会自动发邮件提醒，不用等到某天手动查数据才发现"原来三天前就没更新了"。数据库定期备份，同步一份到云端对象存储，避免单机故障导致数据全丢。

回头看这个项目，虽然一开始的想法很朴素——就是想看看数据分析能不能在这个市场上找到确定性的机会——但做到现在，从数据采集、数据库设计，到机器学习建模、严谨的回测方法论，再到工程化的部署和监控，基本上把一个量化交易系统该有的模块都走了一遍，而且是真金白银在跑，不是停留在纸面上的回测报告。
